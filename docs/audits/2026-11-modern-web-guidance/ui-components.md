Scope: all of `src/common/components` (incl. icons, FilterToggleSection), `src/common/tour`, every feature module under `src/modules`, `src/app` route components, and `views/` (incl. `views/shared/components`). ## Findings

### [High] Review cards open their full-text modal from a non-focusable `<div>` that also wraps other controls
- Guide: `ui-components/card` — "use a native link for navigation. When the whole card is one destination, a single link may wrap the `<article>` only if the card contains no other interactive elements (`a`, `button`, `input`, `select`, `textarea`)" and "Elevate interactive elements with `position: relative; z-index: 1` so they remain operable."
- Where: `src/modules/reviews/components/ReviewItem/ReviewItem.tsx:31-40`, `src/modules/reviews/components/ReviewItem/ReviewModal/ReviewModal.tsx:68`, `src/modules/reviews/components/ReviewItem/ReviewBody/ReviewBody.tsx:11` (`line-clamp-5 md:line-clamp-3`)
- Problem: `<DialogTrigger asChild>` is applied to a plain `<div className="focus-ring … cursor-pointer">`. Radix Slot only adds `type`, `aria-haspopup`, `aria-expanded` and `onClick`. It adds no `tabIndex` and no role, so the trigger is not focusable and is not announced as a button. Review bodies are clamped to 3–5 lines, and the modal is the only place to read the whole review, so keyboard and screen-reader users cannot read full reviews. The same `div` also wraps vote, reaction, share and report buttons, the course link (`RevieweeCourse` ProgressLink) and tooltip trigger buttons. Every child has to call `stopPropagation()` to avoid opening the modal by accident (for example `reaction-picker-button.tsx:26-29`, `ReviewReactionsGroup.tsx:39-41`).
- Fix: Render the card as `<article>`. Put one real `<button type="button">` in the card heading (or a "Read full review" button), make it the `DialogTrigger`, and stretch its hit area with `after:absolute after:inset-0` on a `relative` card. Give the footer actions and links `relative z-10` so they stay clickable above the overlay, as `MeetingCard.tsx` already does. Once the bubbling `onClick` is gone, the `stopPropagation()` calls can be removed.

### [High] Adding a reaction only works on hover (Radix HoverCard), and the emoji handler sits on an inner `<span>`
- Guide: `ui-components/hovercard` — "Only use hovercards to provide supplemental information (e.g. a preview of information that can otherwise be obtained by clicking on the link), never information that is not available in any other way."
- Where: `src/common/components/reaction-picker-button.tsx:32-62`. Used by `src/modules/reviews/components/ReviewItem/ReviewReactionButton/ReviewReactionButton.tsx:15` and `src/modules/roadmaps/components/RoadmapReactionButton.tsx:9`.
- Problem: The "React" button's `onClick` calls `preventDefault()` and does nothing else. The emoji palette is a `HoverCardContent`, and Radix HoverCard ignores touch pointers. It opens on keyboard focus, but it is portalled and closes on trigger blur, so Tab never reaches the emojis. Touch, keyboard and screen-reader users therefore cannot add a reaction at all. Each emoji is also a `TooltipTrigger` `<button>` whose `onSelect` handler is on a child `<span>` (line 54). A keyboard Enter/Space dispatches `click` on the button, not on the span, so even a focused emoji would do nothing. A tooltip inside a hover card is a second hover-only layer.
- Fix: Make the "React" button a click/tap trigger for a `Popover` (Radix `Popover`, or native `popover` + `popovertarget`), with a labelled group of `<button type="button" aria-label="Like" aria-pressed={…} onClick={() => onSelect(label)}>` emoji buttons. Drop the nested Tooltips; `aria-label` plus visible emoji is enough. After that, `@radix-ui/react-hover-card` has no other consumer and can be removed from `package.json`.

### [High] `TagToggleGroup` hides its checkboxes with `display:none`, so the filters cannot be used from the keyboard or by assistive technology
- Guide: `ui-components/card` — "use a radio button or checkbox with an associated `<label>`, or an `option` in a native `<select>`, when the card is a choice." Also `ui-components/checkbox` — "**DO NOT** use `outline: none` or hide focus indicators on checkboxes."
- Where: `src/common/components/tag-toggle-group.tsx:27-52`. Used at `src/modules/bidding/components/BidAnalyticsClient.tsx:272` (Round filter), `:286` (Window filter) and `src/modules/submit/components/ReviewForm/ReviewFormSection.tsx:237` (review label tags).
- Problem: The Radix `CheckboxPrimitive.Root` gets `className="hidden"`, which is `display:none`. That removes it from the tab order and the accessibility tree. The visible `Tag` is a `<div>` with a no-op `onClick`. Mouse users can toggle through the `<label>`, but keyboard and screen-reader users cannot reach or operate the bid-analytics Round/Window filters or the review-form tags. The same `ref` is also attached to every checkbox.
- Fix: Use a native, visually hidden checkbox inside the label, and style the chip from its state: `<label className="has-[:checked]:… has-[:focus-visible]:ring-2"><input type="checkbox" className="sr-only" checked=… onChange=…/>{label}</label>`. Alternatively use the existing Radix `ToggleGroup type="multiple"`, which gives `aria-pressed`. Wrap each group in `role="group"` with `aria-labelledby` pointing at the "Round"/"Window" caption. Never change `border-width`/`padding` on selection, as the card guide warns.

### [High] Meeting heatmap availability is shown only in a pointer-hover card; keyboard and touch users get colour alone
- Guide: `ui-components/hovercard` — "Use the **Interest Invokers** API to trigger the hovercard. This ensures the card appears on both hover and focus." Also: "Link previews and tooltips on action controls qualify; anything the user needs belongs in a toggletip or inline."
- Where: `src/modules/meetings/components/grid/HeatmapHoverCard.tsx:72-95` (only `pointerover`/`pointerleave` listeners), `:111-121` (JS-clamped `position: fixed` box with `role="tooltip"`), and `src/modules/meetings/components/grid/MeetingMatrixGrid.tsx:245-249` (cell `aria-label` is only the date and time).
- Problem: Who is available in each slot, and how many people, is the core information of the meetings heatmap. It appears only when a mouse pointer moves over a cell. Heatmap cells are focusable `<button>`s, but focusing one shows nothing, and its accessible name has no counts. Touch users see only the background colour, and screen-reader users hear "Tue 4 Nov 10:00" with no availability at all. That fails WCAG 1.4.1 (colour alone) and 1.3.1.
- Fix: (1) Add the tally to each cell's name, for example `aria-label={`${date} ${time}, ${available.length} of ${participants.length} available`}`. (2) Also listen for `focusin`/`focusout` on the container, so the shared card follows keyboard focus as well as the pointer. (3) Optionally move the card to `popover="hint"` with CSS anchor positioning (`position-area: block-start; position-try-fallbacks: flip-block, flip-inline`) instead of manual `getBoundingClientRect` clamping (`ui-atoms/position-aware-tooltips`: "Prefer logical fallbacks"). Keep the JS path as the fallback, because interest invokers and `position-area` are not Baseline Widely available.

### [High] The global "/" shortcut swallows "/" in every text field and also closes the search dialog
- Guide: `ui-components/dialog` — "**DO** open declaratively with `command="show-modal"` and `commandfor` on a `<button>`." The guides do not cover global shortcuts directly; this is a functional bug in the dialog's open path.
- Where: `src/modules/search/components/SearchCmdk/SearchCmdk.tsx:76-86`. It is active wherever `<SearchCmdk />` is rendered without `asChild`, which is `src/modules/home/components/AppSidebar/AppSidebar.tsx:182` (the desktop sidebar, on every page).
- Problem: The `document` `keydown` listener runs `e.preventDefault(); setOpen(o => !o)` for every `/` press, without checking the event target. Users cannot type "/" in any input or textarea: review text ("and/or"), meeting-link URLs (`https://…`), assistant chat, roadmap names. Each attempt opens the search modal instead. Inside the open search input, typing "/" toggles the modal shut.
- Fix: Ignore the shortcut when `e.defaultPrevented`, when a modifier key is held, or when `e.target` is editable: `(e.target as HTMLElement).closest('input, textarea, select, [contenteditable=""], [contenteditable="true"]')`. Only open the dialog, never toggle it closed, from the shortcut.

### [Medium] Assistant widget is a hand-rolled non-modal dialog: no Esc, and focus is dropped on open and close
- Guide: `ui-components/dialog` (Rule 2) — "Use `<dialog popover>` for a top-layer panel with popover dismissal (`auto` light-dismisses, `manual` does not)." For the modal case it notes "The browser provides: inert page, focus containment, top layer, `::backdrop`, `Esc` and back-gesture dismissal, and focus return to the invoker." The popover gives Esc and focus return for this non-modal case.
- Where: `src/modules/assistant/assistant-widget.tsx:51-141` (launcher hidden at `:59`, `<div role="dialog">` at `:70-87`, close button at `:121-130`)
- Problem: Clicking the launcher sets `hidden` on the focused launcher itself, so focus falls to `<body>` and nothing moves it into the panel. Closing with the X sets `hidden` on the panel while focus is inside it, so focus is lost again instead of returning to the launcher. There is no `Escape` handling. Screen-reader users get no cue that the panel opened. (The expand toggle also changes its label while using `aria-pressed`; `ui-components/toolbar` says toggle buttons "use `aria-pressed`… Do not change their label when toggled".)
- Fix: Render the panel as `<dialog popover="manual" aria-label="AfterClass assistant">` (or a `div` with `popover="manual"`) and open it with `showPopover({ source: launcher })`. On open, focus the chat input (or the panel heading). On close, focus the launcher before hiding. Add an `Escape` keydown on the panel that closes it, and keep the visible close button. Keep the launcher in the DOM, or move focus before hiding it. Keep a constant label ("Expand widget") with `aria-pressed`.

### [Medium] `Progress` never exposes its value, and its instances have no accessible names
- Guide: `ui-components/progress` — "**Use a native `<progress>` element**: It provides built-in accessibility and platform-consistent behavior." Also: "Use `<label for="...">`, `aria-labelledby`, or `aria-label` to associate the progress element with a label."
- Where: `src/common/components/progress.tsx:8-27` (`value` is destructured and used only for the indicator transform; it is never passed to `ProgressPrimitive.Root`). Instances: `src/modules/bidding/components/BidPredictionCard.tsx:102`, `:122`; `src/modules/home/components/GlobalProgressBar/GlobalProgressBar.tsx:20`. Hand-rolled: `views/roadmap-view/view.tsx:96-100` (`role="progressbar"` with no name).
- Problem: Radix sets `aria-valuenow` only from the Root's `value`, so every `Progress` is announced as an indeterminate, unnamed progressbar. The two BidPredictionCard bars show "Odds of having other bids" and "Confidence level". Those are measurements, not task progress. Assistive technology hears neither the label nor the number.
- Fix: Replace the wrapper with native elements. Use `<meter min={0} max={1} value={p} aria-labelledby=…>` for probabilities and confidence (and the assistant quota meter, `quota-meter.tsx:56-62`). Use `<progress value max aria-label="Loading page">` for `GlobalProgressBar`, or mark that decorative bar `aria-hidden`. Style with `appearance:none` and the separate `::-webkit-progress-value` / `::-moz-progress-bar` rules (the guide says "Do NOT group `-webkit-` and `-moz-` pseudo-elements in the same rule"). This removes `@radix-ui/react-progress`. If Radix is kept, at minimum pass `value` to the Root and require a label. `<progress>` and `<meter>` are Baseline Widely available.

### [Medium] Success-rate slider (rc-slider) has no accessible name or value text; prefer a native range

Then remove `rc-slider` and its global CSS import. In the view, give the legacy range `tabIndex={-1}` and `aria-hidden`, or remove it.

### [Medium] Toasts fired while a modal dialog is open are hidden from assistive technology (verify)
- Guide: `ui-components/persistent-toast-notifications` — "**DON'T** surface toast notifications in the background while a modal dialog is open. It's likely the notification will be missed. Instead, suppress the notification until the modal dialog is dismissed."

### [Medium] Theme toggle can never return to "System", and it pins a scheme that may match the OS
- Guide: `ui-components/dark-mode-toggle` — "In all cases, the UI MUST support reverting or setting the color scheme to system." Also: "If the target matches the current system preference, the user is undoing their adjustment: remove the stored value. - Where: `src/common/components/theme-toggle.tsx:18-31`. Related: `src/common/styles/shadcn.css:56` hard-codes `color-scheme: light` on `:root`, while the guide says "the base declaration MUST stay `light dark`".

### [Medium] Scroll-to-top button unmounts while it has focus
- Guide: `ui-atoms/scroll-position-aware-elements` — "When hiding elements that are dependent on scroll position, account for loss of focus when the control disappears."
- Where: `src/common/components/scroll-to-top-button.tsx:23-37`
- Problem: Activating the button scrolls to the top, which makes the sentinel visible, and `if (isVisible) return null` then removes the focused button. Focus drops to `<body>`, so a keyboard user's next Tab starts from the top of the document.
- Fix: Before scrolling, move focus to the page's main heading or skip target (`tabindex="-1"`). Alternatively keep the button mounted and hide it with `opacity-0 pointer-events-none` (plus `inert` only when it is not focused). The guide's `container-type: scroll-state` approach is Limited availability, so keep the IntersectionObserver as the fallback.

### [Low] Assistant welcome bubble behaves like an auto-dismissing toast mounted as a live region
- Guide: `ui-components/persistent-toast-notifications` — "**DO** add toast notifications consistently to the same container in the page, so that people using assistive technologies can consistently locate them." Also: "**DO** use `ariaNotify()` to announce the content present in toasts".
- Where: `src/modules/assistant/welcome-bubble/welcome-bubble.tsx:71-111`
- Problem: The `role="status" aria-live="polite"` element is mounted together with its text (`if (!visible) return null`), and live regions inserted with their content are often not announced. It contains two buttons, auto-dismisses on a timer, and closes on any `Escape` pressed anywhere on the page.
- Fix: Keep an empty polite region mounted permanently and write the message into it, or call `document.ariaNotify?.(message)` with the region as the fallback. Pause the auto-dismiss on hover and focus-within. Scope `Escape` to when focus is inside the bubble.

### [Low] Onboarding tour (driver.js) auto-starts on page load as a modal overlay (verify focus behaviour)
- Guide: `ui-components/persistent-app-tours` — "Focus must not be moved to these popovers on page load." Also: "**MANDATORY:** Use `popover="manual"` to prevent the tour step from closing accidentally during user interaction."
- Where: `src/common/tour/useAutoStartTour.ts:21-27` (auto-starts 1.2 s after mount), `src/common/tour/tour.ts:32-46`
- Problem: driver.js draws a page-blocking overlay and, by default, takes keyboard focus into its popover. That interrupts users who arrived with a task, which the guide asks to avoid. Tour copy that points at "here" or "this button" also depends on visual context.
- Fix: Don't auto-start; offer the tour via the existing `TourReplayButton` or a dismissible inline prompt. If auto-start stays, configure driver.js not to steal focus, or build steps as `popover="manual" role="dialog" aria-labelledby` panels tethered with anchor positioning, as the guide shows. Keep each step's text self-contained.

### [Low] Search dialog trigger nests a disabled `<input>` (and a tooltip trigger) inside a `<button>`
- Guide: `ui-components/dialog` — "**DO** use a native `<button>` with an accessible name for close controls." and "**DO** open declaratively with `command="show-modal"` and `commandfor` on a `<button>`." The guide wants a real, named button as the invoker.
- Where: `src/modules/search/components/SearchCmdk/SearchCmdk.tsx:116-124`, `src/modules/search/components/SearchCmdk/SearchCmdkModalTrigger/SearchCmdkModalTrigger.tsx:16-30`
- Problem: `DialogTrigger` (a `<button>`) wraps an `InputRoot` with a `disabled readOnly` `<input value="Search">` and a `Kbd` tooltip trigger. Interactive content inside a button is invalid HTML, and the name is derived inconsistently. The onboarding tooltip is attached to non-focusable content and is opened by a timer.
- Fix: Render a styled `<button type="button" aria-keyshortcuts="/">` with a search icon, visible "Search" text and a decorative `<kbd aria-hidden>`. Show the onboarding hint as inline text or a dismissible popover instead of a timed tooltip.

### [Low] Breadcrumb current page is a fake link, separators are list items, and the current page truncates
- Guide: `ui-components/breadcrumbs` — "Mark the current page, the last item, as a link with `aria-current="page"`. Keep it a link (not plain text)". Also: "Dividers are decorative. Do not put them in the markup as text." Also: "keep every item on one line and never truncate the current page."
- Where: `src/common/components/breadcrumb.tsx:51-79` (`<span role="link" aria-disabled="true">`, `<li role="presentation">` separators), `src/modules/home/components/Breadcrumb/Breadcrumb.tsx:32-45` (`max-w-80 truncate` on `BreadcrumbPage`; `BreadcrumbLink` is a plain `<a>`, so navigation does a full reload instead of using `next/link`)
- Fix: Render the current item as `<a href={current} aria-current="page">`. Draw separators with `li + li::before { content: "/" / ""; }` (or a masked chevron) instead of extra `<li>`s. Truncate ancestor labels only. Use `BreadcrumbLink asChild` + `<Link>`.

### [Low] Text truncated with `title` as the only way to read it

- Where: `src/modules/timetable/components/BidTableRow.tsx:84-86` (professor cell `truncate` + `title`), `src/modules/settings/agents/mcp-url-box.tsx:26-29`, `views/roadmap-view/view.tsx:166-169` (course name only in `title` on a code chip), `views/timetable/view.tsx:371`

### [Low] Generic `Card` and `Tag` building blocks lack semantics
- Guide: `ui-components/card` — "use `<article>` as the card root, whether or not it links to a destination". Also "**Header**: a heading on its own." And "keep links and buttons for independent actions as separate native controls".
- Where: `src/common/components/card.tsx:5,31` (`Card` and `CardTitle` are `<div>`s; 10 `CardTitle` call sites); `src/common/components/tag.tsx:214-258` (the delete control is `<div role="button" tabIndex={0} aria-label="Delete">`, the same "Delete" name for every chip, for example each meeting link in `MeetingLinksField.tsx:118-126`; props are not spread, so callers cannot pass ARIA, refs or `data-*`)

### [Low] Scrollable table wrappers are not named, focusable regions, and tables have no captions
