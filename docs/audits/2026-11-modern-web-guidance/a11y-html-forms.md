## Findings

### [High] Auth email/password inputs have no programmatic label; `aria-invalid`/`aria-describedby` land on a `<div>`
- Guide: `accessibility/accessibility` — "Mandatory - Provide a label for all form controls" and "Explicitly associate `<label>` with its control via `for`/`id`"; `forms/forms` — "DO always associate `<label>` with its input using `for` and `id`."
- Where: `src/modules/auth/components/fields/EmailField.tsx:44-58`, `src/modules/auth/components/fields/PasswordField.tsx:46-58`, mechanism in `src/common/components/form.tsx:107-124` (`FormControl` is a Radix `Slot`).
- Problem: `<FormControl>` wraps `<InputRoot>` / `<PasswordInputRoot>` (a `div`), so the Slot puts `id={formItemId}`, `aria-invalid` and `aria-describedby` on the wrapper div, not on the `<input>`. `<FormLabel htmlFor={formItemId}>` therefore points at a div; the email and password inputs on login, signup, forgot-password and reset-password are **unlabelled** (only the placeholder gives them a name), and the RHF/zod error text ("Invalid email or password…") is never associated with or announced on the input. Clicking the label does not focus the field either.
- Fix: move `<FormControl>` inside, directly around the real control: `<InputRoot>…<InputControl><FormControl><Input {...field}/></FormControl></InputControl></InputRoot>` (same for `PasswordInput`), or have `FormControl` accept a `asChild`-style target and pass `id`/`aria-*` to the `<input>`. Add a unit test asserting `getByLabelText("School Email Address")` returns the `<input>`.

### [High] Sign-in/sign-up autofill tokens, input types and constraints are wrong
- Guide: `forms/autofill-sign-in-form` — "MANDATORY: Use `autocomplete="current-password"` for the password input in a sign-in form." and "MANDATORY: Add the `required` attribute to both email and password fields."; `forms/autofill-sign-up-form` — "MANDATORY: For a sign-up form, use `autocomplete="new-password"`." and "Don't double up inputs"; `html/html` — "DO match `autocomplete` tokens with appropriate `inputmode` and `type` (`type="email"` + `inputmode="email"` + `autocomplete="email"`)".
- Where: `src/modules/auth/components/fields/EmailField.tsx:50-56` (`autoComplete="on"`, no `type`), `src/modules/auth/components/fields/PasswordField.tsx:55` (`autoComplete="on"` for both sign-in and new-password contexts), confirm-password field `src/modules/auth/components/SignupForm.tsx:105-113`; used by `LoginForm.tsx:130-161`, `SignupForm.tsx:87-113`, `ForgotPwdForm.tsx:209-217`, `ResetPasswordForm.tsx:296-303`.
- Problem: password managers cannot tell sign-in from sign-up/reset (no strong-password suggestion on signup/reset, wrong fill on login); the email field is `type="text"`, so mobile gets no `@` keyboard and no native validation; no `required`, `spellcheck="false"`; signup forces the password twice.
- Fix: give `EmailField` `type="email" autoComplete="username" spellCheck={false} required enterKeyHint="next"`; give `PasswordField` an `autoComplete` prop and pass `"current-password"` (LoginForm) or `"new-password"` (SignupForm, ResetPasswordForm), plus `required minLength={8}` and `enterKeyHint="done"` on the last field. Drop `confirmPassword` (the show-password toggle already covers it). All Baseline Widely available.

### [High] Required review rating cannot be operated by keyboard or screen reader
- Guide: `accessibility/accessibility` — "Prefer HTML elements and attributes to ARIA" / "Validate Sequential Navigations using keyboards alone … confirm every interactive element is reachable and operable"; `forms/forms` — "DON'T use generic `<div>`, `<span>`, or `<a>` elements for form controls." and "DO use `<fieldset>` and `<legend>` … to group related controls."
- Where: `src/common/components/rating-group.tsx:28-40` (clicks on `<svg>` hearts), `:117-127` (wrapper is `role="img"`); used for the required "Rating *" fields at `src/modules/submit/components/ReviewForm/ReviewFormSection.tsx:212-228`.
- Problem: the hearts are SVGs with `onClick` only: not focusable, no role, no keyboard handling, and the container is exposed as a single image. Keyboard and screen-reader users cannot set a rating, so they cannot submit a review at all (rating is required by `reviewFormSchema`). `FormControl` also passes `id`/`aria-invalid`/`aria-describedby`/`ref` that `RatingGroup` drops, so the label points nowhere and RHF cannot focus the field on error.
- Fix: render an interactive variant as a native radio group: `<fieldset><legend>Course rating</legend>{[1..5].map(n => <label><input type="radio" name="course.rating" value={n} className="sr-only peer" required/> <HeartIcon aria-hidden/> <span className="sr-only">{n} of 5</span></label>)}</fieldset>` with `peer-focus-visible:outline-2` on the heart; keep `role="img"` only for the `readOnly` display. Forward `ref` to the first radio so `handleSubmit` can focus it.

### [High] Review "labels" tags are unfocusable (hidden checkbox) and share one `id`
- Guide: `forms/forms` — "DO hide inputs visually using the canonical `.visually-hidden` recipe … NOT `display: none`, which removes them from the accessibility tree."
- Where: `src/common/components/tag-toggle-group.tsx:28-41`; used for required tags at `ReviewFormSection.tsx:230-246`.

### [High] Reactions on reviews and roadmaps are hover-only (unusable by keyboard and touch)
- Guide: `accessibility/accessibility` — "confirm every interactive element is reachable and operable"; `html/html` — "DON'T use generic `<div>` or `<span>` when semantic elements exist, for instance for interactive elements".
- Where: `src/common/components/reaction-picker-button.tsx:26-29` (the "React" button's `onClick` only calls `preventDefault`/`stopPropagation`), `:52-58` (`<span onClick>` per emoji inside a Radix `TooltipTrigger` button); used by `ReviewReactionButton.tsx:15` and `RoadmapReactionButton.tsx:9`.
- Problem: the emojis are only reachable by hovering the button to open a Radix `HoverCard`, which does not open on touch. The portalled content is not next in Tab order, and pressing Enter/Space on the emoji `TooltipTrigger` button fires the button's click, not the inner span's, so `onSelect` never runs from the keyboard. Touch and keyboard users cannot add reactions.
- Fix: make the "React" button open a `Popover` (click/tap + keyboard, focus moves in) and render each emoji as a `<button type="button" aria-label={toTitleCase(label)} onClick={() => onSelect(label)}>`; drop the inner `<span onClick>`.

Change `focus:outline-none` to `focus-visible:outline-hidden` at minimum.

### [Medium] Enter-to-submit handlers are not IME-safe
- Guide: `forms/ime-safe-enter-submit` — "For a `<textarea>` or `<input>` with custom enter-to-submit, check the native `isComposing` property of the `KeyboardEvent` before submitting the content."
- Where: `src/modules/assistant/composer.tsx:36-41` (chat textarea), `timetable/components/VariantSwitcher.tsx:328`, `timetable/components/BidsDashboard.tsx:90`, `roadmaps/components/RoadmapList.tsx:159,291`, `assistant/session-list.tsx:122`, `meetings/components/shared/MeetingLinksField.tsx:74`. There is no `isComposing` check anywhere in the repo.
- Problem: Japanese, Chinese and Korean IME users send half-composed messages or rename to partial text when they press Enter to confirm a candidate.
- Fix: `if (e.key === "Enter" && !e.shiftKey) { e.preventDefault(); if (e.nativeEvent.isComposing || e.keyCode === 229) return; form.requestSubmit(); }`. The `keyCode === 229` check is the guide's fallback for Safari, where `isComposing` is not supported. Where possible, drop custom Enter handlers in favour of a `<form onSubmit>` (native implicit submission is already IME-safe).
